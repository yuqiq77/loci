# Loci v0.2.0 Memory/Context Addendum

| Field | Value |
| --- | --- |
| Status | Draft addendum |
| Date | 2026-06-30 |
| Scope | Recent continuity snapshot, request-time context assembly, timestamp/watermark strategy, incremental consolidation |
| Related docs | `docs/specs/v0.2.0.md`, `docs/memory-capsule-design.md`, `docs/retrospective-v0.1.2.md` |

This addendum keeps the existing v0.2.0 spec intact and records the follow-up
design correction from the memory/context discussion: long-term continuity and
recent cross-session working state should be separate account-level inputs, read
fresh at generation time.

## 1. Design correction

Do not copy account-level memory into a session when the session starts. A
session owns its event log; account-level continuity is a dependency fetched for
each assistant turn.

Each generation should assemble context from:

1. the current session history and session summary;
2. the latest account-level long-horizon narrative;
3. the latest account-level recent continuity snapshot;
4. query-relevant anchors from memory rows;
5. the current user message.

This explains the desired old-thread behavior: an old thread keeps its old
messages, but when the owner returns to it, the provider request sees the latest
account-level state. The thread is not rewritten; the context assembly is fresh.

## 2. Continuity layers

| Layer | Scope | Update mode | Context role |
| --- | --- | --- | --- |
| Raw message history | Per session | Immutable event log | Source of truth; cursor-bounded in prompt |
| Session summary | Per session | Rolling replacement summary | Current thread state |
| Long-horizon narrative | Account-level | Low-frequency consolidation | Long-term identity, history, recurring patterns |
| Recent continuity snapshot | Account-level | Frequent overwrite | Recent projects, decisions, open questions, near-term shifts |
| Memory rows / anchors | Account-level rows | Insert/update/soft-delete; decay in scoring | Retrieved details in volatile tail |

The key new layer is the recent continuity snapshot. It is the missing middle
between a slow, long-term long-horizon narrative and lucky per-turn retrieval.

## 3. Recent continuity snapshot

The recent continuity snapshot is a short owner-level rolling document answering:
"what has been active lately across sessions?"

It is not a durable memory store and not a second long-horizon narrative. It is
small, dated, overwritten, and allowed to expire.

### 3.1 Scope

- One global snapshot for the owner, not one per thread.
- Carries cross-session current state: active projects, recent decisions,
  unresolved near-term questions, and meaningful short-term shifts.
- Lets an old thread rejoin the owner's current life without relying on a memory
  retrieval hit.

### 3.2 Storage

Add a single-row table:

```sql
create table recent_continuity_snapshot (
  id integer primary key check (id = 1),
  content text not null default '',
  version integer not null default 0,
  updated_at timestamptz not null default now(),
  source_window_start timestamptz,
  source_window_end timestamptz,
  source_summary_ids jsonb not null default '[]'::jsonb,
  source_memory_ids jsonb not null default '[]'::jsonb,
  stale_after timestamptz
);
```

`stale_after` is optional but recommended. If the snapshot is missing or stale,
context assembly should omit it rather than invent a substitute.

### 3.3 Budget

Add a setting:

```text
recent_snapshot_token_budget: target 150-300 tokens inside the capsule
```

The snapshot is bounded before it enters the capsule. It should not compete with
the session recent-message window.

### 3.4 Generation

The `update_recent_snapshot` job reads recent account-level inputs:

- session summaries whose cursor advanced recently;
- sessions active since the last snapshot window;
- high-salience memory rows changed recently;
- unresolved `open_thread` rows;
- recent `shift` rows;
- pinned or high-importance rows only when relevant to the current window.

It writes a replacement snapshot, not an append-only log.

The prompt should prefer removing stale or resolved items over preserving them:

```text
Maintain a short account-level snapshot of what has been active recently.
Capture current projects, recent decisions, open questions, and near-term
shifts. Do not store durable facts or long-term history here; those belong in
the long-horizon narrative and memory rows. Drop stale or resolved items. Return
only the replacement snapshot.
```

### 3.5 Triggers

Do not run this synchronously on the chat hot path.

Recommended triggers:

- when a session summary cursor advances;
- after an assistant turn, through a debounce or low-frequency job;
- manual "consolidate now";
- scheduler/nightly job;
- conceptual "session close" if the app later has a reliable close event.

Avoid treating browser tab close as a durable semantic event. Web sessions often
do not close cleanly.

## 4. Timestamp and watermark strategy

The current schema already has useful time fields:

- `sessions.created_at`
- `sessions.updated_at`
- `messages.created_at`
- `messages.completed_at`
- `memories.created_at`
- `memories.updated_at`

Use `created_at` to understand when something began. Use `updated_at` or
completion timestamps to find recent activity. A thread created months ago but
continued today is recent.

### 4.1 Recommended session fields

Keep `sessions.updated_at` for list ordering / latest user activity, and add an
explicit completion marker if needed:

```text
sessions.last_completed_at
```

This should update when an assistant response completes successfully. It gives
snapshot/consolidation jobs a clean "this thread produced a complete new turn"
watermark without overloading `updated_at`.

If no new column is desired initially, compute it from:

```sql
select max(completed_at)
from messages
where session_id = $1 and status = 'complete';
```

### 4.2 Snapshot watermarks

`recent_continuity_snapshot.source_window_end` is the primary watermark.

When updating the snapshot:

1. use previous `source_window_end` as the start point;
2. include a small overlap window, such as 6-24 hours, to avoid missing late
   background jobs;
3. scan changed sessions, summaries, and memories in that window;
4. write the new snapshot and advance `source_window_end`.

The overlap means source IDs should be retained for dedupe/debug, but the model
still emits a replacement snapshot, so duplicate source rows should not create
duplicate prose.

## 5. Long-horizon narrative consolidation

The long-horizon narrative remains the long-term carrier. It should not become a
project-status tracker; that is the recent snapshot's job.

### 5.1 Current plan from v0.2 docs

The v0.2 docs already intend consolidation to be incremental by default:

- `consolidate_narrative` reads the current long-horizon narrative plus recent
  salient inputs;
- it rewrites the single narrative as a bounded replacement document;
- it keeps recent versions for rollback/debug;
- low-frequency rebuild mode regenerates from raw history and full memory rows
  to remove accumulated rewrite drift.

So consolidation does not need to rescan all conversations every time.

### 5.2 Recommended narrative storage

```sql
create table relationship_narrative (
  id integer primary key check (id = 1),
  content text not null default '',
  version integer not null default 0,
  updated_at timestamptz not null default now(),
  last_incremental_window_end timestamptz,
  consolidation_count integer not null default 0,
  last_rebuild_at timestamptz
);

create table relationship_narrative_versions (
  id uuid primary key default gen_random_uuid(),
  narrative_version integer not null,
  content text not null,
  created_at timestamptz not null default now(),
  source_window_start timestamptz,
  source_window_end timestamptz,
  mode text not null check (mode in ('incremental', 'rebuild', 'manual'))
);
```

Retain only the most recent 7 versions unless the owner explicitly exports or
pins more.

### 5.3 Incremental consolidation

Default mode:

```text
current long-horizon narrative
+ salient source rows since last_incremental_window_end
=> replacement long-horizon narrative
```

Candidate incremental sources:

- new or changed `boundary_fact` rows;
- high-importance `shared_moment` rows;
- meaningful `shift` rows;
- unresolved or newly resolved `open_thread` rows;
- recent session summaries that contain durable account-level changes;
- manual profile edits or curated standing-context changes.

Incremental consolidation should filter for long-term significance. Routine
current-state changes belong in the recent snapshot instead.

### 5.4 Rebuild mode

Rebuild mode is low-frequency and intentionally more expensive:

```text
raw history + full memory rows + current durable profile sources
=> fresh long-horizon narrative
```

Use it:

- every K incremental consolidations;
- on manual "consolidate now" if the owner requests a full rebuild;
- after major schema/prompt changes;
- when the narrative appears drifted or contaminated.

The raw message log and memory rows are the safety net that make rebuild mode
possible.

## 6. Request-time context assembly

Per assistant turn:

1. Fetch the session summary and recent complete turns after the summary cursor.
2. Fetch latest `relationship_narrative`.
3. Fetch latest non-stale `recent_continuity_snapshot`.
4. Fetch unresolved open threads that are eligible for capsule inclusion.
5. Retrieve query-relevant anchors into the volatile tail.
6. Deterministically assemble the continuity capsule under budget.
7. Build the provider request with stable content before cache breakpoints and
   volatile content after them.

No LLM call should happen during assembly. Synthesis happens in background jobs:
summary, extraction, snapshot update, and narrative consolidation.

## 7. Cache model

The cached prefix is version-stable, not session-frozen.

```text
cached prefix:
  system prompt
  continuity capsule
    - long-horizon narrative version N
    - recent continuity snapshot version M
    - session summary version/cursor C
    - eligible open threads
  settled recent history

volatile tail:
  query-retrieved anchors
  current user message
```

The prefix busts once when one of its source versions changes, then stabilizes
again. Per-turn anchor retrieval stays in the tail and should not invalidate the
cached prefix.

## 8. Provenance and trust

Memory and continuity inputs should retain source metadata:

- source session/message IDs;
- source type: `explicit_user`, `implicit_conversation`, `tool_output`,
  `manual_profile`, `system_bootstrap`;
- importance/confidence;
- freshness or source window;
- whether the owner manually edited or confirmed it.

Tool outputs are brittle. By default, tool-derived observations should remain
short-term/session-local or enter the recent snapshot with low confidence. They
should not enter the long-horizon narrative unless corroborated, explicitly
confirmed, or manually curated.

## 9. Implementation order

Recommended low-risk path:

1. Add `recent_continuity_snapshot` table and a snapshot token budget setting.
2. Add deterministic capsule assembly that can initially consume existing
   `standing_context`, current session summary, and the snapshot.
3. Add `update_recent_snapshot` job with source windows and stale handling.
4. Add long-horizon narrative storage and version history.
5. Add `consolidate_narrative` incremental mode.
6. Add rebuild mode and manual "consolidate now".
7. Move retrieved memories from folded current-user text into a dedicated
   anchors tail block.
8. Add context tracing that records narrative version, snapshot version, summary
   cursor, selected anchors, and cache breakpoints.

This order lets the recent-state layer land before the full long-horizon
narrative machinery, while keeping the current raw-message and summary model
intact.
