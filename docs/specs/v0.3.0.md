## 1. Theme

v0.2.0 makes continuity reliable on the chat path: recent snapshot, continuity
capsule, kind-aware anchors, repetition suppression, and cache-aware placement.
v0.3.0 should not replace that path. It should add a background **memory
organization layer** that turns flat memory rows into entities, episodes, and
eventually long arcs while preserving the existing request-time shape.

The goal is not "more memory in every prompt." The goal is better source
organization, better consolidation inputs, and better browsing/debugging.

Design stance:

- Keep PostgreSQL as the single source of truth.
- Keep chat assembly deterministic and model-call-free.
- Add tables and jobs around the existing `memories` rows; do not fork the
  memory system into SQLite/Chroma/MCP.
- Prefer a few stable abstractions over a full clone of any reference system.

## 2. Organization and diagnostics

### 2.1 Memory organization

The proposed archive organizes existing `memories` rows in PostgreSQL:

- extract atomic fragments;
- link them to named entities;
- consolidate related fragments into episodes;
- optionally connect episodes into long arcs;
- expose the links for browsing and inspection.

The entity/episode/arc layers extend the existing store and background jobs.

### 2.2 Memory diagnostics

Diagnostics should explain retrieval and scoring using the existing memory,
embedding, and `memory_injections` tables.

Adopted now:

- `importance`, `valence`, `arousal`, `resolved`, and manual `pinned` flags;
- kind-aware thresholds and arousal-resistant decay;
- injection traces with suppression reasons.

Still missing and pulled into v0.3:

- a dry-run memory debug endpoint;
- a memory health endpoint;
- a UI that explains recall decisions;
- pinned/anchor scarcity guidance and diagnostics.

## 3. Position relative to v0.2.0

v0.3.0 builds on these v0.2 assumptions:

| v0.2 layer | v0.3 role |
| --- | --- |
| `memories` rows | Remain the atomic source rows. v0.3 links them to entities and episodes. |
| `recent_continuity_snapshot` | Still carries recent cross-session state. v0.3 may feed it better inputs, but does not replace it. |
| Continuity capsule | Still the only standing request-time context block. v0.3 outputs may enter the capsule only through existing narrative/snapshot channels. |
| Anchors tail | Still the per-turn retrieval surface. v0.3 can add entity/episode candidates to retrieval after MC-105, but anchors remain volatile tail data. |
| Long-horizon narrative | Remains the long-term prose carrier. v0.3 episodes are inputs to consolidation, not a second always-on narrative. |

This means v0.3 is safe to ship incrementally. If every v0.3 job is disabled,
chat should behave exactly like v0.2.

## 4. Memory Debugging and Health

Before adding more memory layers, v0.3 should make the existing layer
observable through health summaries and retrieval score breakdowns.

### 4.1 Memory Pulse

Add a read-only health summary for the memory subsystem:

- active memory count and trash count;
- count by `kind`;
- pinned count;
- unresolved `open_thread` count;
- rows with missing embeddings;
- duplicate exact hashes among active rows, if any;
- recent `memory_injections` totals by `suppression_reason`;
- injected vs. suppressed rate over the last 7 days;
- top recalled memories by `recall_count`;
- stale-but-pinned or unresolved-old-thread warnings.

This is not a tuning surface. It is a "why does memory feel strange today?"
surface.

### 4.2 Retrieval Dry Run

Add a dry-run endpoint that accepts a query and returns the same candidate
analysis as chat retrieval without writing traces and without updating recall.

Each candidate should expose:

- memory id, kind, content preview;
- similarity;
- kind-specific similarity gate;
- recency weight;
- emotional score contribution;
- importance and pinned contribution;
- final score;
- salience result;
- repeat-suppression result, when session context is supplied;
- token-budget inclusion/exclusion result;
- final decision: would inject / would suppress, with reason.

The dry run explains candidate selection using the same scoring path as chat.

### 4.3 Memory Trace View

Use the existing `memory_injections` table to show recent decisions for one
memory:

- where it was injected;
- where it was suppressed;
- similarity and score at the time;
- suppression reason;
- linked session/message.

This answers "why does this keep coming up?" and "why did this never come up?"
without guessing from the current row alone.

### 4.4 Pinned and Anchor Guidance

`pinned` stays manual. Diagnostics should show the effect of pinned status
and make overuse visible:

- a pinned count and soft recommended range;
- candidates that may deserve pinning because they are repeatedly injected,
  high-importance, or high-arousal;
- pinned rows that never get retrieved, so the owner can unpin or rewrite them;
- a warning if too many pinned rows make "pinned" meaningless.

No automatic pinning in v0.3.

## 5. New Memory Organization Layers

### 5.1 Entities

Entities are named things the conversation repeatedly touches: people, places,
projects, works, events, interests, and recurring concepts.

Proposed table:

```sql
create table memory_entities (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  kind text not null,
  aliases jsonb not null default '[]'::jsonb,
  overview text not null default '',
  status text not null default 'seed',
  evidence_count integer not null default 0,
  first_seen_at timestamptz,
  last_seen_at timestamptz,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);
```

Proposed junction:

```sql
create table memory_entity_links (
  entity_id uuid not null references memory_entities(id) on delete cascade,
  memory_id uuid not null references memories(id) on delete cascade,
  confidence real not null default 0.5,
  source text not null default 'classifier',
  created_at timestamptz not null default now(),
  primary key (entity_id, memory_id)
);
```

Rules:

- Start with cheap name/alias matching and conservative LLM classification in
  background jobs only.
- New entities begin as `seed`; promote to `active` after repeated evidence.
- Entity overviews are short and replaceable. They are browsing/consolidation
  inputs, not prompt payload by default.

### 5.2 Episodes

Episodes are compact narrative summaries generated from a cluster of related
memory rows, usually under one entity or a small group of linked entities.

Proposed table:

```sql
create table memory_episodes (
  id uuid primary key default gen_random_uuid(),
  title text not null default '',
  content text not null,
  embedding vector(1536),
  importance real not null default 0.5,
  valence real not null default 0,
  arousal real not null default 0,
  status text not null default 'active',
  source_memory_ids jsonb not null default '[]'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  deleted_at timestamptz
);
```

Proposed junction:

```sql
create table memory_episode_entities (
  episode_id uuid not null references memory_episodes(id) on delete cascade,
  entity_id uuid not null references memory_entities(id) on delete cascade,
  primary key (episode_id, entity_id)
);
```

Rules:

- Episodes are generated offline from existing memory rows and entity links.
- Episodes do not delete or replace source memories.
- Episodes may later participate in anchor retrieval with a boost, but only
  after MC-105's cue-gated anchor behavior is stable.
- Episodes are high-quality inputs for long-horizon narrative consolidation.

### 5.3 Arcs

Arcs are long-running cross-entity themes: "how this project evolved", "a
recurring philosophical thread", "a repeated emotional pattern".

Arcs are intentionally deferred until entities and episodes prove useful.
Treat arcs as optional consolidation artifacts, without adding a separate
emotional-state engine.

## 6. Jobs

### 6.1 `classify_memory_entities`

Runs over new or changed memory rows.

Steps:

1. Use name/alias matching against active entities.
2. If no confident match, ask the compression provider to propose entity links
   and seed entities.
3. Write `memory_entity_links`.
4. Promote seeds when evidence passes a code constant threshold.

This job must be idempotent. Re-running it should converge, not duplicate rows.

### 6.2 `refresh_entity_overviews`

Runs on active entities whose linked memories changed.

Output is a bounded replacement overview:

- what the entity is;
- why it matters to the person;
- active unresolved points, if any;
- no durable facts invented beyond linked sources.

### 6.3 `consolidate_memory_episodes`

Runs when an active entity has enough unconsolidated linked memory rows.

Output is one or more bounded episodes. Source memories are marked only by
provenance, not deleted or hidden. A later v0.3 ticket can add a lightweight
`consolidated_at` marker if needed.

### 6.4 `refresh_memory_arcs` (Deferred)

Runs low-frequency, if at all. Reads episodes and entity overviews, then writes
long arcs. Do not ship until dogfooding shows episodes alone are insufficient.

## 7. Retrieval

v0.3 retrieval should be staged:

1. Keep v0.2 memory-row anchors unchanged.
2. Add episode retrieval as an experimental second channel, behind code-level
   feature gating.
3. Fuse row and episode candidates with reciprocal-rank fusion only after trace
   data shows episode retrieval improves relevance.
4. Entity aggregation can be added for explicit named queries: if the user names
   a known entity, pull a small recent set of linked rows/episodes.

Retrieval output still formats as anchors in the volatile tail. The assistant
should not see "entity tables" or "episode internals"; it sees useful context.

The retrieval dry-run endpoint from §4 must support every retrieval channel that
ships. If entity/episode retrieval is added, debug output must show which
channel produced each candidate and how fusion changed the ranking.

## 8. UI

v0.3 should add a practical debug UI before a decorative memory map.

Recommended first UI:

- memory pulse dashboard;
- retrieval dry-run form;
- per-memory trace drawer;
- pinned diagnostics;
- existing memory list links to debug details.

Recommended second UI:

- entity list with search/filter by kind;
- entity detail page showing overview, linked memories, and episodes;
- episode detail showing source memories;
- manual merge/split/delete controls only after the automatic layer is stable.

The star-map visualization is optional. If built, it should be a browsing view
over `memory_entities` and links, not a separate data model.

## 9. Non-Goals

- No SQLite or ChromaDB sidecar.
- No external MCP memory server.
- No jiwen/emotional-state engine.
- No always-on injection of all entities or episodes.
- No autonomous per-turn archival model call.
- No destructive migration of existing `memories` rows.
- No automatic pinning.
- No owner-facing scoring sliders.

## 10. Migration Strategy

All schema changes are additive.

Recommended order:

1. Add memory debug/pulse read helpers and UI.
2. Add entity/link tables.
3. Add entity classifier job and tests.
4. Add entity browsing UI.
5. Add episode tables.
6. Add episode consolidation job and tests.
7. Feed episodes into long-horizon narrative consolidation.
8. Only then experiment with episode/entity retrieval.

Rollback expectation: disabling v0.3 jobs and ignoring v0.3 tables returns the
system to v0.2 behavior.

## 11. Acceptance Scenarios

1. Existing chat, memory extraction, recent snapshot, and capsule behavior are
   unchanged when v0.3 jobs have not run.
2. The debug page can explain why a query would inject or suppress each top
   candidate without mutating recall or trace state.
3. The pulse page shows memory health, missing embeddings, pinned count, and
   recent suppression distribution.
4. A memory detail can show its recent injection/suppression history from
   `memory_injections`.
5. Pinned remains manual, but the UI makes pinned scarcity visible.
6. A repeated person/project/place becomes an active entity after multiple
   linked memories.
7. Entity overviews are short, source-grounded, and do not enter the prompt
   unless retrieved or consolidated through v0.2 channels.
8. Episodes preserve source links and improve long-horizon narrative
   consolidation quality without deleting source rows.
9. Named-entity queries retrieve more specific context than flat vector search.
10. Old shared moments still do not surface unprompted in unrelated chat.
11. The memory UI can explain why an entity or episode exists by showing source
   memory rows.
