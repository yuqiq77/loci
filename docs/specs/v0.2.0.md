## 1. Theme

v0.1.0 proved durable chat with summaries and a fact-style memory store. v0.2.0
reorients memory from a **profile of the user** toward a **record of the
shared history**, and adds a small, opt-in set of agent capabilities (limited
tools, proactive messages) plus image input — all individually switchable and
off by default.

Guiding principle for memory: continuity is not a database of attributes
about one party; it is the evolving, shared context produced by talking. The
system should let a new conversation resume rather than reconstruct the person.

**Design stance.** Memory is a bounded projection of retained evidence.
Retrieval salience may decay and narrative detail may be reduced over time.
Keep the controls inspectable and the scoring model small; preserve access
to source evidence without loading a complete archive into every request.

## 2. Memory Model Redesign (centerpiece)

### 2.1 Three carriers

| Layer | Role | Mutability | Always in context? |
| --- | --- | --- | --- |
| Raw message history (`messages`) | Source of truth | Immutable | No (cursor-bounded) |
| **Long-horizon narrative** | **Primary carrier of continuity** | Rewritten (consolidated) | **Yes** |
| Memory rows (`memories`) | Secondary, retrievable detail | Kept (soft-delete only); decay in weighting | Only when retrieved |

The long-horizon narrative becomes the backbone of cross-conversation
continuity. Memory rows stop being the main carrier; they supplement the
narrative with specific, retrievable detail. Raw history remains the immutable
substrate everything is rebuilt from.

### 2.2 Long-horizon narrative

A single, owner-level (single-user), evolving prose account written in the
assistant's own voice — "where we are, what we've been through, what's unresolved" —
distinct from per-session summaries.

- **Scope**: one global narrative for the owner (not per-thread) — continuity is
  the whole history's, not a single conversation's.
- **Storage**: one row in a new `relationship_narrative` table (`id` fixed,
  `content text`, `version int`, `updated_at`). Retain the **most recent 7
  versions** in a side table; a bad rewrite (drift) is the main risk and version
  history is cheap insurance.
- **Generation**: a `consolidate_narrative` job reads the current narrative plus
  recent salient inputs (new/changed memory rows, recent session summaries, open
  threads) and **rewrites** the narrative — it does not append. Bounded length
  to stay lean (this is also the token lever).
- **Rebuild mode**: incremental rewrites compound lossy edits over time (the same
  decay a rolling summary suffers, at whole-history scope). Consolidation therefore
  also supports a low-frequency **rebuild** that regenerates the narrative from
  raw history and the full memory rows instead of from the current narrative,
  skipping accumulated drift. Immutable raw history is what makes this possible;
  it runs every K consolidations or on the manual "consolidate now". Default
  consolidation stays incremental.
- **Trigger**: nightly consolidation (shares the proactive scheduler) **plus a
  manual "consolidate now"** owner action. Never on the per-turn path.
- **Injection**: the narrative is never injected raw. It feeds the continuity
  capsule (§2.5) as the "long-term shared context" component.

### 2.3 Memory rows, reframed

Extraction stops asking "what facts or preferences should be remembered?" and
asks instead whether the conversation contained any of:

1. a **stable fact or boundary** that should prevent future mistakes;
2. a **meaningful shared moment** worth preserving;
3. a **shift** in the user's thinking, project, or emotional state;
4. an **unresolved thread** future conversations should be able to resume.

This maps to a new `kind` on each memory row:

```
memory_kind = boundary_fact | shared_moment | shift | open_thread
```

`kind` lets retrieval and decay treat rows differently (§2.4) and feeds other
features (open_threads drive "what to resume" and proactive digests). Existing
`importance`/`valence`/`arousal`/`resolved` are retained; `resolved` is the
natural lifecycle flag for `open_thread`.

### 2.4 Forgetting via decay (not deletion)

Rows are never auto-deleted and raw history is never touched. Forgetting is
expressed as **retrieval down-weighting**: a long-unrecalled, low-salience row
falls below the similarity/score threshold and effectively drops out, while
remaining recoverable and visible in the memory page.

Decay is **asymmetric by kind**:

- `boundary_fact`: no decay (it exists to prevent mistakes).
- `open_thread`: no decay until `resolved`.
- `shared_moment`: gentle decay, strongly resisted by emotional intensity and
  `pinned`.
- `shift`: moderate decay (superseded by later shifts).

This extends the existing recency term rather than replacing the scoring model.
Decay constants live in code in v0.2; the memory page **shows** a row's current
standing (e.g. faded/active) read-only — no owner-facing decay dials.
Observability over tunability.

### 2.5 Injection: continuity capsule + anchors

Storage and injection are separated. The three carriers each keep their storage
role, but the request never injects all three raw. The context builder produces
**one continuity capsule** (a fixed-budget state block, target 600–900 tokens)
plus a small set of **relevant anchors**.

```
[ cacheable prefix — stable within a session; see §2.6 ]
1. System prompt
2. Continuity capsule              (standing state; capsule_token_budget)
   - long-term shared context       (from the long-horizon narrative)
   - current thread state           (= session summary when a cursor exists; else empty)
   - open threads                   (unresolved open_thread rows)
3. Recent complete turns           (after the summary cursor; recent_message_budget)
[ volatile tail — re-computed every turn; never cached ]
4. Relevant anchors                (query-retrieved; small cap)
   - relevant boundary_fact rows    (low similarity threshold; they prevent mistakes)
   - relevant high-salience shared_moment rows
5. Current user message
```

Anchors moved **after** recent turns (not early), so that per-turn-volatile
retrieval lives in the uncached tail and does not bust the cached prefix (§2.6).
The capsule stays early because it is stable within a session and belongs in the
cached prefix; the volatile tail is small (a few anchors plus the user message).

Design rules:

- **Assemble, do not generate, per turn.** The capsule is a deterministic
  assembly of already-synthesized parts (the narrative is consolidated offline,
  the session summary by the summary job, open threads/boundaries are rows). No
  per-turn model call. `buildContinuityCapsule()` is a pure, unit-tested
  function with a hard budget.
- **No summary/recent overlap.** The summary cursor already partitions history:
  the summary covers messages through the cursor, recent turns load after it.
  The capsule's "current thread state" is the session summary only when a cursor
  exists (long thread); a short thread injects no summary and relies on recent
  turns. The summary replaces over-long history, it never restates recent turns.
  This thread-state summary is the **re-scoped, length-capped** session summary
  (working state of this thread only; durable facts/preferences live in memory
  rows and the narrative, not here — see `summaries/summarize.ts`), not a
  durable-fact store.
- **Open-thread injection is consolidation-timed, not write-timed.** An
  `open_thread` row created mid-session does **not** enter the capsule the moment
  it is written; it enters at the next consolidation/summary boundary. Within the
  session that opened it, the thread is still resumable from recent turns. This
  keeps the capsule (and thus the cached prefix, §2.6) stable within a session;
  capsule stability is favored over immediate inclusion.
- **Standing vs retrieved, to bound capsule size.** Only the narrative, thread
  state, and open threads are standing (all bounded: the narrative is length-
  capped, unresolved threads are few). `boundary_fact` never decays and
  accumulates, so boundaries are **retrieved** (relevant-now, low threshold),
  not all-always-injected. Ordinary `shared_moment` rows are not injected by
  default — only currently relevant, high-salience ones become anchors — so the
  assistant does not parade old moments to perform familiarity.

### 2.6 Prompt caching and breakpoint placement

Long conversations are too expensive without cache hits, so the injection layout
is explicitly cache-aware. Anthropic prompt caching is prefix-based: the content
up to a `cache_control` breakpoint is cached and only hits on a later request if
that prefix is byte-identical. The rule is therefore **stable content before the
breakpoint, volatile content after it**.

- The **cached prefix** is system prompt + continuity capsule + settled history.
  The capsule is stable within a session (the narrative changes nightly, the
  thread state only when summarization advances, open threads only occasionally);
  history is append-only. "Open threads only occasionally" is enforced, not hoped:
  mid-session `open_thread` writes enter the capsule only at a consolidation/
  summary boundary (§2.5), so a new thread never busts the prefix the turn it is
  created.
- The **volatile tail** is the query-retrieved anchors and the current user
  message. These change every turn and must sit after the last breakpoint, so
  they never invalidate the cached prefix.
- **Breakpoints (2 of the 4 allowed):**
  - one on the capsule end (the top-level `system` block carries system prompt +
    capsule), and
  - one rolling breakpoint on the **last settled history message** (not the
    current message, as the pre-v0.2 code did).
- **The capsule goes in the top-level `system` block; anchors do NOT.** The
  current `toAnthropicRequest` folds every system-role message into the top
  `system` field. In v0.2 the capsule may go there (stable, cached), but anchors
  must be injected as a block in the `messages` tail (after history, before the
  current user message) so they stay out of the cached prefix.
- When the capsule changes (consolidation) or the cursor advances
  (summarization), the prefix busts **once**, re-writes, and recovers — occasional,
  not per-turn. Per-turn anchor retrieval is preserved; only its position moves
  to the uncached tail, where its cost (a few rows) is negligible against the
  cache-read price of the history.

This supersedes the pre-v0.2 caching layout (breakpoint on the last message,
memory folded into `system`), which busts every turn once long-term memory is
active. See `legacy/pre-v0.2.0.md`.

### 2.7 Schema and jobs

- New table `relationship_narrative` (+ optional `relationship_narrative_versions`).
- `memories` gains `kind memory_kind not null default 'shared_moment'`.
- New job types: `consolidate_narrative`; optional one-off `backfill_memories`
  and `backfill_narrative` to seed from existing history.
- New migration required (v0.2 may add migrations).

## 3. Capability Toggles

A `capabilities` group in settings, all booleans, agentic ones default **off**:

```
memory_enabled            (master; embeddings still gate retrieval)
tools_enabled
web_search_enabled
proactive_enabled
image_input_enabled
```

Each gates its code path at the server boundary (not just UI). The default
experience stays a calm assistant; turning a switch on is an explicit choice.
Toggles must exist before the features they gate ship.

## 4. Context and Token Management

- Add `capsule_token_budget` (target 600–900) and an anchor count cap; keep
  `context/recent/memory` budgets. The capsule replaces raw narrative/summary
  injection rather than adding a layer.
- Document explicit priority ordering (§2.5) and trim by relevance, not only by
  recency: lowest-scored anchors first, then oldest turns, never the system
  prompt, capsule, or current message. Within the capsule, trim the narrative
  component first (thread state and open threads are cheap).
- Use the provider token-count endpoint for budgeting, with the `ceil(chars/3)`
  estimator as fallback when the provider does not support it (so an unsupported
  provider never blocks).
- The narrative being short is load-bearing for both continuity quality and
  token cost — consolidation must enforce a length cap so the capsule fits its
  budget by assembly alone.
- **Cache-aware layout (§2.6) is the main cost lever for long threads.** Keep the
  stable capsule + history in the cached prefix and the volatile anchors + current
  message in the uncached tail; this turns per-turn input cost from roughly
  quadratic toward linear in conversation length.

## 5. Image Input

- `ModelMessage.content` becomes a content-block array (`text` | `image`);
  `ChatRequest` and the Anthropic adapter carry image blocks.
- Composer gains image attachment; gated by `image_input_enabled`.
- **Storage**: images go on a mounted volume, referenced by path in message
  metadata — not base64 inline, which would bloat and dirty the message rows.
  Image bytes never live in the message body.
- Token budgeting must account for image cost. Embeddings/memory remain
  text-only; a `shared_moment` may reference an image via metadata.

## 6. Limited Tool Calling

- `ChatChunk` gains a `tool_use` variant; orchestration becomes a bounded loop
  (model → `tool_use` → execute → `tool_result` → continue) with a hard
  iteration cap. The `messages.role` enum already includes `tool`.
- Allowlist only:
  - `get_user_time` — local; returns current time in the settings timezone.
    Anthropic has no native time tool, so this is a trivial client-side tool;
    zero dependency / zero trust surface, a safe first tool.
  - `search_memory` — internal; reuses vector retrieval; safe.
  - `web_search` — external dependency; adds network egress; gated separately.
- Tool results are **untrusted data**, wrapped like memories and never treated
  as instructions (prompt-injection surface, especially `web_search`).
- Gated by `tools_enabled` / `web_search_enabled`.

## 7. Proactive Messages

- A lightweight scheduler enqueues a `proactive_digest` job at configured local
  times (e.g. 09:00 / 21:00, settings timezone). The scheduler is shared with
  nightly narrative consolidation.
- The job reads the long-horizon narrative, open threads, and recent material,
  composes a short message, and posts it as an assistant message into a
  dedicated "Daily" session, visible on next app open. No push notification in
  v0.2.
- Idempotent per day; gated by `proactive_enabled`.

Existing `EMBEDDING_*` / `COMPRESSION_*` unchanged. New optional: `WEB_SEARCH_*`
(provider key/endpoint) only when `web_search_enabled`. No secrets in settings.

## 10. Non-Goals (v0.2)

- External memory runtimes and storage services.
- Multi-user.
- Open-ended autonomous agent loops (tools are a fixed allowlist with a cap).
- Push notifications / mobile background delivery.
- Semantic memory merge (decay + narrative consolidation are expected to manage
  bloat; revisit if rows still proliferate).
- Vector index tuning (still exact scan).

## 11. Decisions (resolved)

| Decision | Choice | Rationale |
| --- | --- | --- |
| Narrative scope | One global narrative | Single-user assistant; continuity is the whole history's, not a thread's |
| Consolidation trigger | Nightly + manual "consolidate now" | No per-turn cost; nightly is natural and shares the proactive scheduler; manual gives the owner agency |
| Prior narrative versions | Retain most recent 7 | Drift is the top risk; version history is cheap insurance |
| Image storage | Mounted volume + path in metadata | Base64 inline bloats/dirties message rows; bytes don't belong in the body |
| Tokenizer | Provider count-tokens, `chars/3` fallback | Count tokens properly when budgeting matters; fallback avoids blocking on unsupported providers |
| Proactive landing | Dedicated "Daily" session | Doesn't pollute a working session or inject into a project context |
| Decay exposure | Code constants + read-only UI | Observability over tunability; no decay dials to over-tune |
| Capsule assembly | Assemble-only per turn | All synthesis stays offline (consolidation/summary); per-turn stays cheap |

## 12. Risks

- **Narrative drift / lossy rewrite**: a bad consolidation could drop continuity
  or invent it. Mitigation: immutable raw history allows rebuild; retain prior
  versions; constrain the prompt to consolidate from sources, not invent; run a
  periodic full **rebuild-from-sources** consolidation (§2.2) so incremental
  rewrites do not compound drift unboundedly.
- **Forgetting something that mattered**: kind-asymmetric decay, `pinned`, and
  never-decay boundary facts guard against this.
- **Context bloat**: narrative + summary + memories + recent risks *more* tokens,
  the opposite of the goal. Hard per-bucket budgets and a short narrative are
  required.
- **Injection via tools/images/web**: treat all external/tool content as data.
- **Proactive surface**: proactive messages and affect-weighted memory stay
  owner-controlled — toggles off by default, everything visible and editable.

## 13. Suggested Phasing

1. **Memory redesign + toggles + context/token** (the core; toggles first so
   later features have a gate). Migration for `kind`, narrative table, budgets.
2. **Limited tool calling** — `search_memory` first (no external dep), then
   `web_search`. Shares the provider-boundary refactor with images.
3. **Image input** — done with the same `ModelMessage`/`ChatRequest` reshape as
   tools.
4. **Proactive messages** — needs the scheduler; reuses it for nightly
   narrative consolidation.

Per the change policy, increment the architecture version when the memory
carriers, context order, or provider request shape change.

## 14. v0.1.2 handoff — what landed, what MC-101/102 inherit

v0.1.2 shipped interim subsets of this spec so dogfooding could continue. They
compose with v0.2 rather than being thrown away. Detail and rationale:
[`../memory-capsule-design.md`](../memory-capsule-design.md) and
the private v0.1.2 retrospective (not in this snapshot).

**Landed in v0.1.2 (MC-101/102 build on these):**

- **Cache-aware layout (§2.6 subset).** Stable content in the cached prefix,
  volatile in the tail; the rolling `cache_control` breakpoint is on the last
  settled history message (not the current turn). MC-102 keeps this and adds the
  capsule/anchors split.
- **Standing context = interim capsule.** An owner-curated profile + long-horizon
  narrative (`settings.standing_context`), injected as a cached leading system
  block, budget `STANDING_CONTEXT_TOKEN_BUDGET = 2000`, edited at a dedicated
  `/profile` page. MC-101 migrates this into the `relationship_narrative` store;
  MC-102 replaces the raw block with the deterministically-assembled capsule.
  Voice convention is fixed (capsule design §4): `you` = the assistant (system
  prompt only); user by name; assistant named in third-person sections, `I`/`we`
  in first-person sections.
- **`kind` + kind-aware decay/retrieval.** `memories.kind` is stored; `score.ts`
  does kind-asymmetric, arousal-resisted decay (boundary_fact / pinned /
  unresolved open_thread never decay; shared_moment/shift fade with
  `halfLife = 30·(1+arousal)`; resolved threads sink); `retrieve.ts` gates with a
  kind-aware similarity threshold (boundary_fact lower so it surfaces). This is
  the §2.4/§2.6 decay and surfacing gate, minus anchors.
- **Summary** is thread-state-only and rides in the cached prefix with a bounded
  budget (`SUMMARY_TOKEN_BUDGET`, prompt-enforced; hard truncation deferred to
  MC-102 budgeting).

**Decisions to inherit (recorded so v0.2 does not re-litigate):**

- **Use the existing storage and worker.** Existing pgvector +
  Dockerized Postgres + job worker; consolidation must JOIN raw history with
  memory rows (an external store can't), and an external session-start push
  conflicts with the cached prefix. (capsule design §10.)
- **Narrative is the main line; extraction retreats to a feeder** — it captures
  `boundary_fact` + a few episodic atoms; the bulk/texture is consolidated into
  the narrative from raw history.
- **Semantic dedup/supersede is consolidation's job**, not per-write model
  arbitration. Write-time dedup stays exact-hash; `boundary_fact` supersede may
  use a lightweight rule.
- **Anchor retrieval is cue-gated** (cue signal AND strong similarity);
  `boundary_fact` is exempt (relevance-gated, no cue). LLM rerank is a reserve,
  not the default path.
- **Active surfacing is a proactive behavior** (§7 / the scheduler), not a
  synchronous session-start injection — it would otherwise fight the cached
  prefix.

**Pending for v0.2 (not in v0.1.2):**

- MC-101: `relationship_narrative` table + versions; the `consolidate_narrative`
  job + rebuild mode; reframed extraction tagging; migrate `standing_context`.
- MC-102: deterministic `buildContinuityCapsule`; cue-gated anchor retrieval in
  the tail; capsule in the `system` block replacing the raw standing-context
  block; provider token-count budgeting (hard summary/capsule caps).
- Extraction cadence: extract every few turns over a window (preferably
  piggybacking the summary cursor boundary), not per-exchange.
